# Inclusive and global language

Use this guidance for public-facing prose, examples, people-focused content, accessibility topics, and writing intended for translation.

## Rules

- Use clear, literal language that translates cleanly.
- Avoid slang, idioms, humor, metaphors, culture-specific references, and geographically narrow assumptions.
- Avoid unnecessarily gendered, ableist, violent, demeaning, or patronizing language.
- Use singular `they` when gender is irrelevant.
- Use person-first or identity-first language according to the preference of the community being described.
- Do not describe people without disabilities as "normal" or "healthy."
- Use diverse names, genders, ages, locations, and technical roles without assigning stereotypes.
- Avoid socially charged terms for technical concepts when a precise alternative exists.
- If an established non-inclusive term is unavoidable in existing code, minimize its use, format it as code, explain it once, and use the preferred term in later prose.
- Prefer precise technical descriptions over euphemisms or graphic language.

## Examples and data

Do not use real personal information. Use reserved example domains such as `example.com`, fictional names, reserved phone numbers, and documentation IP ranges. Use meaningful project names such as `staging` or `frontend-development`, not `foo`, `bar`, or `baz`.

## Review checklist

- [ ] The language is literal, respectful, and suitable for translation.
- [ ] Examples avoid PII, stereotypes, and cultural assumptions.
- [ ] Gender and disability language is relevant and respectful.
- [ ] Existing code terms are minimized and do not become new prose or identifiers.
- [ ] No metaphor or idiom is doing technical work that a precise sentence should do.

Source: [Google Write inclusive documentation](https://developers.google.com/style/inclusive-documentation) and [Writing for a global audience](https://developers.google.com/style/translation).
