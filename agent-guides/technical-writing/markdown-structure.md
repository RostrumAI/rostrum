# Markdown structure and formatting

Use this guidance for Markdown headings, paragraphs, lists, tables, notices, and inline formatting.

## Structure

- Use one unique level-1 heading for a document.
- Keep heading levels logical. Do not skip a level, use an empty heading, or repeat the page title as a section heading.
- Use sentence case for headings, titles, navigation, labels, list items, and table content.
- Use a bare verb for procedure headings and a noun phrase for conceptual sections.
- Give each paragraph one main point. Put the distinguishing information first.
- Do not use hard line breaks inside a sentence or paragraph.

## Lists and tables

- Introduce every list with a complete sentence when context is needed.
- Use numbered lists for sequence, priority, or phases; bullets for unordered items; description lists for term-definition pairs.
- Keep list items parallel in syntax, scope, capitalization, and punctuation.
- Do not create a one-item list unless the procedure rule requires a bullet.
- Use tables only when rows have a real two-dimensional relationship. Prefer lists for one-dimensional information.
- Introduce every table with a complete sentence. Use concise sentence-case headings and do not merge cells.

## Inline formatting

- Use bold only for exact UI labels and run-in headings.
- Use italics sparingly for introduced terms, words as words, emphasis, mathematical variables, and standalone work titles.
- Use code font for commands, paths, filenames, parameters, types, method names, constants, enum values, environment variables, database elements, HTTP verbs, status codes, IP addresses, ports, package names, literals, and command output.
- Use fenced code blocks for code samples.
- Reserve underlining for links.
- Use `and`, not `&`, except for exact UI labels, official names, diagram labels, constrained table headings, and code.
- Keep quotation marks and sentence punctuation outside link text.

## Punctuation

Use standard American punctuation, including serial commas. Use a colon when grammar calls for an explanation, list, command, or description. Prefer a period over a semicolon when it is clearer. Use em dashes only for a genuine break, never as list separators. Do not use en dashes as punctuation or range markers. Use hyphens for compounds and number ranges.

## Review checklist

- [ ] Heading hierarchy is complete and logical.
- [ ] Headings and labels use sentence case.
- [ ] Lists are necessary, parallel, and consistently punctuated.
- [ ] Tables express a real two-dimensional relationship and are accessible.
- [ ] Inline formatting communicates semantic meaning.
- [ ] Code, UI labels, links, and literals use the correct format.
