# Documentation review

Use this guidance for a final pass or when reviewing an existing technical document. Read the specialist files that match the document before applying this checklist.

## Technical correctness

- [ ] The text matches current code and behavior.
- [ ] Public API symbols, parameters, returns, exceptions, defaults, and deprecations are documented.
- [ ] Commands and code samples use real syntax and are runnable or clearly scoped.
- [ ] Placeholders are descriptive, consistent, and explained.
- [ ] Performance, cost, security, and comparison claims are scoped and verifiable.
- [ ] Product documentation contains no accidental future promise or release announcement.

## Reader and prose

- [ ] The first sentence states the purpose, behavior, or outcome.
- [ ] The reader and task are clear.
- [ ] Instructions address `you`, use active voice, and put goals or conditions first.
- [ ] Present tense and timeless wording describe product behavior.
- [ ] Sentences are concise, literal, and unambiguous.
- [ ] Terminology, capitalization, and names are consistent.
- [ ] Jargon is removed, defined, linked, or required by the domain.
- [ ] Filler, fake signposting, promotional language, idioms, slang, humor, and unexplained metaphors are gone.
- [ ] `must`, `can`, `might`, and recommendation language express the intended force precisely.

## Structure and formatting

- [ ] The document has one unique level-1 heading and a logical hierarchy.
- [ ] Headings and titles use sentence case without trailing periods.
- [ ] Procedures use numbered steps, with a bullet for one action.
- [ ] Lists are introduced, parallel, and consistently punctuated.
- [ ] Tables are necessary, semantic, introduced, and accessible.
- [ ] Code, filenames, paths, literals, UI labels, links, dates, and units use the correct formatting.
- [ ] Em dashes are not list separators, and en dashes are not used as punctuation or range markers.
- [ ] New prose uses `and` rather than `&` except where an explicit exception applies.

## Accessibility and inclusion

- [ ] Link text makes sense out of context and describes its destination.
- [ ] Images have contextual alt text or `alt=""` when decorative.
- [ ] Complex images have surrounding text, captions, transcripts, or descriptions as appropriate.
- [ ] Meaning does not depend on color, location, images, animation, sound, or punctuation.
- [ ] UI instructions use labels and keyboard-accessible paths rather than visual directions.
- [ ] Examples use fictional, diverse, non-stereotyped data without PII.
- [ ] Language avoids ableist, violent, demeaning, and non-inclusive terms.

If a check fails, edit the content. Do not leave a note that the problem is known or defer an obvious correction.

Source: [Google Highlights](https://developers.google.com/style/highlights) and the [Google developer documentation style guide](https://developers.google.com/style).
