# Procedures

Use this guidance for tutorials, quickstarts, setup instructions, runbooks, and other sequences of actions.

## Rules

- Introduce the procedure with the context or goal the reader needs. Do not repeat the heading.
- Use a numbered list when order matters. Use a bullet for a procedure with one action.
- Put the goal or location before the action: `To create a project, click **File > New > Project**.`
- Keep one meaningful action per step. Combine only small sequential menu choices or actions that are clearer together.
- Start optional steps with `Optional:`.
- Use lowercase letters for substeps and lowercase Roman numerals for sub-substeps.
- For a complex step, use this order: action, command, placeholder explanation, command explanation, output, then result or justification.
- State the action first and the resulting state second: `Click **Run**. The query results appear.`
- Put the tool or UI location before the action: `In the console, go to the **Monitoring** page.`
- Prefer one accessible, short, simple method. Separate genuinely necessary alternatives by heading or tab.
- Link to an existing procedure instead of repeating it.

## UI instructions

Use the exact visible label in bold and name the UI element precisely: `button`, `menu`, `command`, `field`, `dialog`, `page`, `pane`, or `section`. Do not use UI labels as verbs or use directional descriptions such as "left panel" or "above."

## Review checklist

- [ ] The reader knows the goal before taking the action.
- [ ] The steps are in the required order.
- [ ] Each step contains a manageable action.
- [ ] Optional work is marked explicitly.
- [ ] Commands, placeholders, and expected results are explained.
- [ ] The procedure does not duplicate an existing procedure.

Source: [Google Procedures](https://developers.google.com/style/procedures) and [UI elements and interaction](https://developers.google.com/style/ui-elements).
